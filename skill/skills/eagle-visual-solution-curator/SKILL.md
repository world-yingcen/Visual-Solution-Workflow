# 整體視覺方案｜案例分析與 Eagle 整理

讓案例能被找回，也讓後續設計者知道「值得參考什麼、如何成立、轉用時不能丟掉什麼」。使用繁體中文。分類是檢索入口，分析才是設計依據；不能只寫精品感、科技感、有動畫。

## 日常使用與分析範圍

本 Skill 僅服務整體視覺方案。先依使用者指定或目前案件確認方案；只有網址、圖片或「幫我整理案例」而缺少方案脈絡時，簡短確認所屬方案，不自動歸入整體視覺。其他方案交由其適用 Skill，不借用本方案的分類與分析規則。輸出明列「方案：整體視覺方案」；Eagle 資料夾及標籤仍依即時既有分類選擇，不為此標示擅自新增分類。

使用者給案例並說「喜歡這裡，幫我整理」即可開始。先保留其原話或忠實摘要，作為收藏理由；AI 的觀察另列，不能把喜好改寫成客觀結論或用自己的偏好否決收藏。沒說喜歡哪裡時，可先依可見內容提出重點，不為補欄位反覆追問；收藏意圖會影響分析範圍時才簡短釐清。

- 預設聚焦指定區塊，加上理解它所需的前後銜接；只有明確收藏整站才完整瀏覽。不為單一 Banner 啟動全站效能、RWD 或程式碼稽核。
- 優先使用已提供畫面、精確網址或 Eagle 項目。查既有紀錄時先用名稱／網址／相關標籤縮小範圍，沿用有效分析，只補缺項；不掃完整庫、不另外上網找競品或相似網站。
- 需要確認動態就操作該片段，記錄觸發與交接；來源無法載入時用現有資料完成可確認部分，不反覆重試或猜測。技術實作不是收藏重點時，不為辨認框架額外調查。
- 輸出一份精簡、可直接貼入 Eagle 的紀錄。基本欄位為收藏理由、具體手法、適用情境／條件、來源與觀察範圍、分類與標籤；詳細拆解只在有檢索價值時補充。

## 範圍與資料來源

- 接受網址、截圖、影片、既有 Eagle 項目或指定批次。沒有視覺來源時請使用者提供，不憑名稱編分析。
- 需要查詢 Eagle 的既有項目／分類或寫入時，讀同套件 [Eagle 工具規則](../eagle/SKILL.md) 及其整理政策；取得即時資料庫身分與相關資料夾、標籤和目標項目。只讀相關 API 文件，不猜工具參數。純分析使用者提供的網址／圖片可直接開始，不以連線 Eagle 為前提。
- 優先使用使用者指定的資料庫／資料夾／選取項目；沒有指定時唯讀確認目前庫。若有多個合理目標，先問清楚，不自動切庫、不搜尋全機雲端資料夾，也不沿用高效庫的 ID 或分類表。
- 無法連上 Eagle 仍可做視覺分析，但資料夾與標籤標「待取得即時分類」，不把推測詞彙輸出成可直接寫入的既有分類。
- 本 Skill 的修改不等於授權整理真實資料。實際整理先提出完整提案，使用者核准後才寫入；已明確核准的同批項目與分類可直接執行，不重複請示。

## 逐案分析

分析時讀 [案例拆解與輸出](references/case-analysis.md)。

1. 確認收藏目標是整站、整頁、區塊、影像或互動。整站案例保持整體脈絡，不預設每區拆成獨立項目；有獨立檢索需要才建議拆開。
2. 有網址就逐案實際開啟，查看完整的指定收藏範圍及必要上下文。模板介紹頁與實際預覽分開記，不能把模板商品封面當成看過網站。若無法開啟，改分析可讀畫面並明列限制。
3. 記具體構圖、文字層級、影像處理、留白與頁面節奏。互動需實際操作：觸發、開始／過程／結束、反向／重進；手機沒有測就標未驗證。
4. 區分觀察、推論與建議。看起來立體不等於 WebGL，捲動動畫不等於 GSAP；技術名稱須有程式證據或使用者確認。靜態參考本身有價值，不為湊互動欄位捏造動態。
5. 找出設計手法與品牌／內容／體驗的關係，再提出保留特徵與轉用條件。不要強行編造設計師意圖，也不要求每案都符合「打破常規」敘事。
6. 使用者已表達喜歡並要收藏時，保留收藏意圖，指出轉用價值與限制即可。只有使用者要求篩選或評估才提出收錄判斷；模板、老案例或少動畫不自動淘汰，新奇或大量動畫也不自動合格。

## 分類與命名

分類表示大方向，標籤表示可搜尋的具體特徵，備註記如何成立與轉用條件；三者不重複堆同義詞。標籤優先選少量高辨識度詞彙（通常 3–6 個，依既有庫規則調整），例如構圖、影像及已驗證的互動特徵。避免把所有可見元素都標上；動態未驗證就不給會暗示已實測的動態標籤。

- 依即時既有資料夾與標籤挑選，每個選項都要有觀察依據與獨立檢索價值；資料夾用途不重複建成標籤。名稱近似時核對完整路徑與 ID。
- 可從收藏層級、頁面用途、構圖、主體、視覺語言、素材需求、互動方式與網站任務尋找對應入口；這些是分析角度，不代表 Eagle 已有這些分類。
- 整站參考不預設附上所有區塊分類。Footer 等特例依 Eagle 整理政策，不把互動豐富當成隨意增標籤的理由。
- 創意指具體概念或解法，不是「好看」的同義詞。CSS／JavaScript 等泛用技術不加為標籤；特定技術只有已證實、具檢索價值且屬既有核准詞彙時才使用。
- 不合用的分類不要硬套高效的簡潔商業／型錄等選項。缺詞列「建議擴充：類型｜父分類｜名稱｜理由」，不要混入待寫入欄位，也不自行建立新分類。
- 沿用庫內已確認命名規則與既有編號。新案編號無法確定就用「【待編號】品牌／案例－收藏範圍」，不捏造流水號，不替既有項目無故重編號。

## 核准後寫入與回查

- 先回讀目標項目及分類 ID，保存修改前的名稱、備註、資料夾與標籤，記本批核准範圍。資料變動時重新比對，不覆蓋使用者剛補的內容。
- 只用 Eagle 工具／原生介面寫核准欄位，不直接改資料庫 metadata.json。確認 API 是追加還是取代；未被核准移除的既有分類與筆記必須保留。
- 使用小批次更新並回讀核對。失敗、目標不明、分類消失或回讀不符時停下受影響項目，保留其餘成果，不盲目重送或刪除重建。
- 回報實際成功／失敗／未處理數、項目 ID 與未驗證欄位。未寫入就說待審核；工具回傳成功但未回查，不稱已驗證。批准本批不等於日後全庫整理授權。
- 如使用者選手動整理，提供完整資料夾路徑與獨立標籤行；不聲稱貼上資料夾文字即可批次分類。

## 與網站製作的界線

案例備註是觀察與轉用建議，不是客戶已確認的設計指令。用於案件時仍須依 [參考使用方式](../visual-solution-immersive-director/references/mode-routing.md) 確認忠實重建、指定特徵轉譯或原創方向；收藏案例不等於素材可商用或取得重製授權。
