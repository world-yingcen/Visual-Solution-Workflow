# 整體視覺網站設計與製作

交付目標是能在瀏覽器實際體驗、符合品牌與已確認方向的網站。文件支援製作，不代替成品。使用繁體中文與台灣用語。

使用者負責方向、取捨與最後確認；AI 主動整理資料、提案、素材需求與產圖 prompt、實作、觀看與修正，圖片依下方人工操作分工處理。不要要求使用者先想好構圖、動畫或技術解法。

## 單一入口與方案邊界

使用者已授權：本機缺少本輪需要的 Skill 時，依 [Skill 依賴與安裝](references/skill-dependencies.md) 從已確認來源直接安裝，不重複請示。只處理本輪相關 Skill 與必要依賴；同名不同來源或本機修改不覆蓋。網頁／App 缺本機操作能力時明列限制，不假裝已安裝。

本 Skill 是整體視覺製作的唯一主入口，同一任務整合設計、素材、實作與檢查。專項知識按需讀取本 Skill 的 references。不自動啟動多代理。高效方案的模板策略、產圖管道、案例結論與額度換算不能直接移用；歷史案例僅供有標記的參考。

## 2560×1280 桌機優先

動態案件須一起規劃一般模式與減少動態模式：品牌內容、必要功能與完成度一致，差別在動態表現及完整閱讀布局。不能只停掉 GSAP 而保留隱藏內容或 pin 空白；提案依 [動態規範](references/motion-proposal.md)，工程解法依 [Lin-EVO 接入](references/frontend-standards.md) 讀取獨立 Lin-EVO 的 `references/reduced-motion.md`，驗收依 [視覺 QA](references/visual-qa.md)。減少動態不是另開 RWD 階段。

本 Skill 的預設第一階段固定使用 **2560×1280 CSS viewport**，涵蓋核心視覺片段、完整桌機首頁與瀏覽器 QA。構圖、圖片裁切、字級、捲動距離、互動節奏與效能都以這個尺寸實看並記錄；不要以較小桌機畫面代替 2560×1280 驗收。

本階段不做 RWD：不另外設計、實作或驗收 Tablet／Mobile，不產生手機 fallback，不以手機可行性阻擋桌機方向。既有專案若已有 responsive 程式，保留且不要為桌機工作任意刪除，但本輪只保證 2560×1280。只有使用者後續明確要求 RWD，才另立範圍、讀取相應規格並跨裝置驗收；桌機完成不能宣稱 RWD 完成。

使用者依操作手冊已指定「PC 看稿確認後接續 RWD」時，視為已包含後續 RWD 階段，不重複索取授權；仍先完成桌機確認，再切換該階段與驗收尺寸。

## 開始與續作

**設計方向必須有已實際查看與分析的參考。** 依 [設計方向前的參考關卡](references/reference-research.md#設計方向前的參考關卡二擇一)，先查看使用者提供的網站、截圖或影片；沒有可用參考時，必須透過 Eagle MCP／API 或已授權的螢幕控制搜尋並查看參考。已有足夠的使用者參考就不強制連接 Eagle。完成參考分析後才提出設計方向，交由使用者確認；收到連結、工具已連線或看過參考，都不等於方向已確認。兩條路徑都無法取得可分析內容時，先處理參考或工具缺口，不跳過關卡；不受影響的資料整理仍可繼續。純維護文件或接續已確認版型的局部切版不因此重開設計流程。

開案、接續、新增產出及收尾時依 [PRD 與檔案管理](references/project-files.md) 維護：整理新案件與既有案件時，一律依標準目錄歸位，正式網站工程統一放在 `06-切版/`，不是建議選項。頁面／區塊資料集中、有效入口唯一、規格與決策同步、舊試作與目前工作分離；交給 Lin-EVO 切版時也沿用此位置。既有檔案搬移須同步修正引用並驗證，不以保留原位置代替完成整理。由同一任務負責；不再把提案、v1–v8、共用 CSS／JS 和舊試驗散堆同層。

**已完成首次 Git 發布或已 Clone 的網站專案是上述目錄規則的例外**：沿用本機 `project/網站代號/` 的有效 Git 工程與進度正本，不再包一層 `06-切版/`、搬移 `.git`、重新初始化或維護兩份有效工程。**已成功轉 EVO 的案件，原靜態 Git 視同廢棄，僅供查閱；任何修改請至 EVO，不再修改或 push 原 Git。** 只產出匯入包尚不算轉 EVO 完成。

每次開始新一輪工作（包含同一對話中的續作、修改與校稿），都先偵測本輪 Skill 來源及案件工作目錄是否由 Git 管理；有 Git 就先依 [工作前 Git 更新](references/git-workflow.md#每輪工作前更新-git-資料) 更新遠端資料，再重新讀取規範、進度及本輪需要的檔案，才開始工作。不要求使用者每次另說「更新」；捷徑／連結安裝也適用。每個 repo 每輪只檢查一次，讀 references 或重讀入口不遞迴觸發。維護套件本身時同樣先檢查，但保留工作中修改，不為更新覆蓋現況。

- **install.py 安裝**：讀取安裝清單 `~/.claude/skills/.visual-solution-install.json`（Codex 為 `~/.codex/skills/.visual-solution-install.json`）的 `source` 與 `mode`，確認来源與目標後，在來源套件資料夾執行 `python3 install.py --update --target <該安裝清單所在的 skills 目錄>`。Codex 範例：`python3 install.py --update --target ~/.codex/skills`。由安裝器執行 `git pull --ff-only`；案件 repo 另依工作前 Git 更新規則處理，不混用套件安裝器。來源有未提交修改或分歧時保留現況，不自行 reset、stash 或合併。
- **確認本機內容**：捷徑安裝確認指向更新後來源；複製安裝確認已同步。安裝器回報 repo「已經是最新版」不代表安裝副本相同；若副本與來源不同，先確認差異不是使用者本機修改，才用同一來源的 `python3 install.py --copy --target <同一目標>` 同步。缺清單或來源不明時不能猜測目標或覆蓋其他來源 Skill。
- **立即重讀**：更新及同步成功後，重新開啟實際安裝位置的 `SKILL.md` 全文，並讀取本次任務適用的 references，讓本次工作直接使用新版規則，不等下一輪。已有案件確認與使用者指示仍須保留。若執行環境只允許下次載入新版，說明需要重新載入，不宣稱本輪已套用。
- **Claude Code Plugin 安裝**：由 Plugin 更新機制管理，不對 Plugin 快取執行 git pull 或 install.py。每次觸發先透過當下可用的 Plugin 更新能力檢查／更新，再重讀更新後入口；若本環境無法主動更新，明確告知尚未確認最新，提示透過 `/plugin` 更新或啟用自動更新，不能把自動更新設定視為本次已更新的證據。
- **失敗處理**：權限受限時核對來源與目標，再走執行環境的核准流程重試，不修改檔案權限。沒有網路、不是 git clone、來源不明或本機有修改／分歧時，簡短告知原因與目前使用版本，重新讀取現有規則後繼續可做工作，不宣稱更新成功。

遇到 PDF 時，先檢查單一檔案大小：超過 10 MB（10,000,000 bytes）一律明確拒絕讀取，即使使用者要求也不例外；未超過上限才依 [PDF 讀取與暫存](references/project-files.md#pdf-讀取與暫存) 詢問要先讀還是用到再讀。大小未確認或讀取選擇未確認前，不載入 PDF 內容。

先讀案件現有檔案、進度、確認決策與工程限制；PDF 依已確認的讀取選擇處理。已有方向或首頁確認就沿用，不重新提案或重問。資料不完整時先提出有依據的工作假設；品牌／用途完全未知才問最小必要問題。

CIS 不完整或沒有 CIS 時，依 [視覺提案](references/visual-proposal.md) 盤點既有品牌線索，由 AI 提出缺漏項目的具體建議與樣張，交使用者判斷、討論後形成網站視覺約定。工作假設不等於定案；不因缺 CIS 停止提案，也不把 AI 建議當成客戶正式規範。

依 [模式判斷](references/mode-routing.md) 選原創 CREATE、忠實重建 RECREATE，或指定特徵轉譯。參考只是品質基準時，不自行升級成母版。

先讀 [目標範圍與 Aura 基準](references/experience-scope.md)。本 Skill 目前的核心交付是「整體視覺」：以既有品牌內容和資訊為主體，透過專屬構圖、排版、影像整合與裝飾／資訊型互動形成完整網站體驗。若案件要求以新品牌母題、產品儀式或世界觀主導全部互動，標記為品牌賦能需求；先完成品牌概念與主視覺資產，再進本 Skill 的網站製作流程，不假裝一般動態切版足以完成。

案件 PRD 管內容、功能與範圍；Experience Blueprint 管體驗與設計決策。連結既有 PRD，不建立互相衝突的需求來源。

案件製作全程使用 Claude App，依下方「Claude App 與人工操作分工」接續工作，不自動呼叫 Codex 或操作 ChatGPT 產圖。實作規格供同一案件接續使用，不要求使用者在 AI 工具間搬運指令。工具不可用時如實標記缺口，不虛構已讀取本機檔案、已產圖、已測試或已匯入。

涉及切版、程式修改或校稿前，必讀 [獨立 Lin-EVO 接入](references/frontend-standards.md)，依本執行端的 Lin-EVO 安裝配置核對更新方式並重讀共用規範。本方案只補方案差異，不使用歷史工程條文副本。

## 品質與工作方式

使用 GSAP 實作或修正動態時，依 [GSAP 技術 Skills](references/gsap-skills.md) 按需讀取套件內的對應 Skill；它們負責技術正確性，不取代本 Skill 的品牌方向、動態分鏡、本套件工程規範或驗收範圍。

涉及 HTML／SCSS／JavaScript 製作或修改時，必讀 [切版工程規範](references/frontend-standards.md)。這套規則只整合結構、命名、共用元件與初始化；不引入其他方案的母版限制、角色交接或簡單動態上限。既有案件局部修正不自動授權全站重構。

預計使用 EVO 後台的案件，切版前必讀 [EVO 範本查核](references/evo-preflight.md)。由 AI 查工程師套件，在切版時同步實作已核對的逐筆編輯結構與欄位標記，不只列成後續轉檔待辦；同一份來源仍提供完整靜態校稿與互動。設計師不用判斷技術標記；缺契約逐區列待確認。工程師後續處理匯入、必要接入及編輯／儲存／發布驗證，不自動啟動匯入或打包。

本方案的靜態切版需包含搜尋結果頁 `search.html`，供校稿與連結檢查；轉 EVO 時不將它當成必須匯入的自製頁面，改依 Miffy-EVO 與平台原生搜尋功能處理。靜態校稿頁與 EVO 匯入範圍分開記錄。

首次視覺提案、核心試做與完整首頁延伸時讀 [首次產出完成度基準](references/quality-baseline.md)：以關鍵構圖、接近正式品質的素材與真實內容段檢查第一輪。案例用於完成度比較，不套用其品牌風格或驗收結論。

設計時讀 [創意邊界](references/creative-operating-model.md) 與 [設計準則](references/design-constitution.md)。前期明確品牌、目標和品質，保留概念、構圖、材質與技術的探索空間。

- 以品牌內容為主體，先規劃全頁各主要區塊的進入、閱讀、離開與相鄰交接，再深化核心片段。依目的安排重點轉場、輕量銜接與安靜閱讀；不能只設計 Banner，也不讓全站持續強動態。效果須引導視線、解釋內容或延續關係，驗收看完整頁的強弱與閱讀節奏。
- Aura 等偏好案例只校準完成度與方法。依本案產業、品牌定位、受眾、內容與商業任務重新設計，不複製案例的固定風格。
- 構圖、字體、影像、UI 與動態屬於同一個視覺世界，不能只有首屏有設計。
- 不固定黑底、粒子、游標、3D 或框架。先定體驗，再沿用專案技術或提出必要選型。
- 保留正式品牌／產品／角色素材及必要資訊。先把 2560×1280 的資訊、構圖、操作手感與效能做完整。
- 實作自查、視覺判斷和使用者確認分開記錄。分數不是完成證據。

擴展整頁與交付前必讀 [整頁完整度](references/full-page-completeness.md)：保留確認架構、建立場景表、整合品牌素材、安排全頁動態節奏，檢查優惠、信任與 CTA。不能讓使用者逐段提醒缺圖、留白、裁切和後半頁動態。

階段檢查落在實際畫面：視覺提案確認主次焦點及品牌圖形應用；素材置入確認自然度與材質；動態片段驗證相鄰場景交接及反向恢復；整頁交付前自查到 CTA 與 Footer。依上述參考修正可判定的缺陷，再交使用者判斷設計取捨，不把特定案例的圖形或效果固定成每案必做。

## 全站共用導覽與頁尾

- 首頁與所有內頁使用同一套 Nav 與 Footer，Logo、選單順序、字體、尺寸、間距、配色及頁尾資訊配置保持一致；目前頁面的選取標示可不同，不另做內頁版造型。沿用專案共用元件／模板與樣式來源，修改時同步檢查首頁及代表內頁。
- Nav 在頁面向下捲動後固定於視窗頂端，持續可操作，不改成下滑隱藏。頂端與固定狀態、切換門檻由共用規格管理；切換不得造成版面跳動，錨點與焦點目標須避開 Nav 高度，並檢查與釘選動畫的層級關係。
- 首頁與所有內頁在視窗右下角提供一致的 Scroll Top（回到頂部）按鈕，不只放在 Footer。使用可鍵盤操作且有清楚名稱的按鈕或連結；返回頁首需與既有捲動系統相容，減少動態模式不強制平滑動畫。避免遮住 CTA、表單、Cookie 提示或其他浮動工具。
- 交付前實測首頁與代表內頁的頁首、下滑固定狀態、頁尾及回到頂部；確認外觀一致、連結有效、沒有重複導覽或遮擋。此規則不自動擴大 RWD 範圍；使用者明確指定例外時記錄其適用頁面。

## 階段與參考
依 [工作流程](references/workflow.md) 控制階段，只讀當前需要的參考。

預設順序：**客戶資料／CIS／素材盤點 → 路由與方向 → 視覺提案 → 視覺確認 → 動態提案與分鏡 → 動態確認 → 核心片段試做與確認 → 完整桌機首頁。** 不以已完成動畫倒推使用者已確認設計。

1. 理解案件：用 [內容分析](references/client-content-audit.md) 區分事實、策略推論、素材缺口與必要內容。
2. 原創提案：用 [創意方向](references/creative-direction.md) 提 2–3 個概念不同的方向、評分理由與推薦，讓使用者選定。RECREATE 跳過重新發想。
3. 視覺提案與確認：必讀 [視覺提案必備資訊](references/visual-proposal.md)，配合 [體驗藍圖](references/experience-blueprint.md)、[參考研究](references/reference-research.md)、[視覺系統](references/visual-system.md)。實看 CIS 圖頁，交付可觀看的色彩比例、字型、圖示、背景圖騰、形象／人物、功能圖解、目前樣式資產與 2560×1280 關鍵構圖，不以文字清單或互動草稿取代。
4. 動態提案與確認：視覺確認後必讀 [動態提案必備資訊](references/motion-proposal.md) 與 [分鏡](references/scene-storyboard.md)。明列目的、圖層、觸發、起始／過程／結束、速度／停留、轉場／反向、閱讀／CTA、素材、技術風險與減少動態。先展示分鏡，不能把視覺確認延伸成動態核准。
5. 規格與試做：動態確認後讀 [素材製作](references/asset-production.md)、[技術架構](references/technical-architecture.md)、[製作規格](references/production-specification.md)，只深化本輪片段。依 [交接](references/codex-handoff.md) 檢查工程，按 [原型製作](references/prototype-build.md) 實作並啟動預覽。已進入試做階段就完成可操作成果，不只交 Coding Prompt。
6. 觀看與修正：用 [QA](references/visual-qa.md) 在 2560×1280 實測，按 [修正路徑](references/refinement-loop.md) 定位與修正，再給使用者操作確認。
7. 擴展首頁：核心片段成立後展開整頁規格與 2560×1280 桌機首頁，完成桌機驗收與使用者確認。
8. 內頁延伸：使用者要求開始內頁時，必讀 [內頁設計與製作](references/inner-pages.md)。沿用已確認首頁與 PRD，先盤點頁型及平台能力，確認代表頁後展開同類頁。關於我們、ESG、服務等核心頁以首頁完成度設計整頁構圖、區塊進出場、轉場與資訊型互動；查閱／操作型頁面優先清楚穩定。參考站只提供約定的功能結構，不覆蓋本案視覺。RWD 不自動接續，等使用者另外明確要求。

## 各階段模型建議

每次開始／續作或進入新階段，簡短告知「目前階段、建議模型、原因、是否適合切換」，不用每個工具動作重複提醒。使用者已指定模型就遵守；以下是本工作流程的建議分工，不是官方設計能力評測、品質保證或強制門檻。

若平台提供 Astra 與 Sol，以下分別代表高推理／創意整合與主力執行模型；實際名稱、版本及可用性以接收者當下的模型選單／工具資訊為準。其他平台則依相同能力分工選擇，不因名稱不同中止工作。不可宣稱已自動切換，不修改全域預設、不為換模型建立新任務或多代理。模型不可用時說明替代方式，仍沿用既有確認與驗收標準。不推估價格、額度或節省比例；需要比較時另查當下官方資料。

| 階段 | 優先建議 | 使用與切換界線 |
| --- | --- | --- |
| 客戶資料、CIS、內容與素材盤點 | Sol | 適合來源整理、欄位對照與缺漏核對；品牌定位衝突或資料需要跨來源判讀時建議 Astra。 |
| 模式判斷、品牌命題與原創方向 | Astra | 決定原創／指定特徵轉譯／忠實重建，整理保留與可改邊界，避免錯選方向。 |
| 視覺提案與關鍵構圖 | Astra | 統整色彩比例、字體、圖示、人物、背景、功能圖解與素材系統；不只排文件。 |
| 動態提案與分鏡 | Astra | 設計圖層、起承轉合、停留、轉場與反向行為，先確認再實作。 |
| 素材製作與規格整理 | Astra 定方向；Sol 執行已定規格 | 構圖、材質、影像選擇尚未定案時用 Astra；確定後的規格整理、接入與來源記錄可用 Sol。Claude 提供 Prompt，由使用者貼到 ChatGPT 產圖並下載，不把 Prompt 當成已完成素材。 |
| 核心互動片段首次試做 | Astra | 同時處理構圖、技術可行性與動態手感；已確認片段的小修、參數調整可用 Sol。 |
| 完整桌機首頁首次延伸 | Astra | Banner 成立不代表全頁設計已定；仍需完成其餘區塊構圖、素材與全頁節奏。全頁場景及規格均已明確才適合交 Sol 實作。 |
| 已確認版型的主力內頁／資訊頁 | Sol | 沿用確認的視覺系統與元件；遇到新的主視覺、故事或複雜轉場，該部分建議 Astra。 |
| 文案套用、局部樣式微調、一般 bug 修正 | Sol | 不改確認方向；問題跨場景、根因不明或修正反覆失敗時，建議 Astra 深入判斷。 |
| 瀏覽器 QA 與整頁視覺複核 | Sol 做功能／內容檢查；Astra 做視覺／動態總評 | 都必須實看、實測；不能用模型名稱代替證據或使用者驗收，不要求自動啟動第二代理。 |
| RWD（僅另行授權後） | Sol | 保留已確認桌機構圖，處理斷點與跨裝置驗證；需要重新編排敘事或互動時建議 Astra。 |
| 交付整理／已授權部署 | Sol | 核對檔案、啟動方式、測試與未完成事項；模型建議不構成部署授權。 |

**切換前留下依據**：在既有進度檔記下目前階段、已確認／未確認項目、不可改的 CIS／構圖／內容、素材與預覽路徑、動態規格、已知問題及下一步。不要另造一套文件，也不要讓接手模型重開提案或簡化已確認動態。

建議提醒例：「現在進入完整首頁首次延伸，建議繼續 Astra，因為其他區塊的構圖與動態仍需設計；整頁確認後，文案與間距細修就適合切 Sol。」若使用者仍選 Sol，照既定範圍執行，不反覆阻擋。

## Claude App 與人工操作分工

案件全程使用 Claude App，不另行詢問工具分工，不自動啟動多代理或跨工具派工。既有確認、素材位置與下一步記入同一份進度。

- **整體視覺 Skill**：負責開案到核心片段確認的設計工作（盤點、模式判斷、方向、視覺提案、動態分鏡、素材方向、核心片段試做與全頁場景表），以及設計一致性的複核。
- **Lin-EVO**：核心片段經使用者確認，且本輪規格與素材齊全後，由 Claude App 讀取 Lin-EVO，依 [實作規格交接](references/codex-handoff.md) 完成桌機首頁；PC 看稿確認後依已授權範圍完成 RWD，再接續內頁與修正。Lin 自行讀取工程規範，不要求使用者重貼技術條文。
- **Miffy-EVO**：靜態版確認且使用者要求轉 EVO 時，由 Claude App 讀取 Miffy-EVO 處理轉換與匯入成果。未實際匯入、儲存或發布的部分分開標記，不以靜態完成代替後台驗證。
- **人工產圖**：Claude 依 [素材製作](references/asset-production.md) 整理用途、構圖、比例、Prompt、檔名及 `image/` 資料夾的完整位置；使用者將 Prompt 貼到 ChatGPT 產圖，確認後下載。Claude 實際取得完成檔後才檢查與置入；轉檔、壓縮由使用者自行處理。正式 Logo、產品、角色與 IP 使用客供原檔，不生成近似版。

需要使用者提供檔案或操作後台時，列出具體步驟；僅知道本機路徑不代表 Claude App 能讀取。Eagle 的授權螢幕操作只用於參考搜尋與查看，不延伸成自動控制 ChatGPT 產圖。

## 確認與持續推進

設計確認點分為方向、視覺提案、動態提案、核心片段、完整桌機首頁。記錄版本與確認項目。使用者回覆「ok／好」只確認當時明確呈現的範圍；不能從靜態視覺推定動態通過，也不能從片段推定整頁通過。尚未展示的結果不能視為已確認。

一般素材處理、細節、程式修正與重驗在已授權範圍內連續執行，不逐步請示。使用者明確授權 AI 代選或改變節點時記錄並遵守；已有確認不重問。只修改流程文件時不啟動客戶製作。

效果不成立就定位與修正，不包裝成「完成，之後可優化」。同一根因修正兩輪仍無改善就改變假設或做小型替代驗證；需更換已確認方向或缺關鍵資產時，提出具體差異供決策。

## 接續與完成

使用者說「下班、先離開、換電腦、換對話、整理 handoff」時，依 [離開前交接與換電腦續作](references/project-files.md#離開前交接與換電腦續作) 更新唯一交接紀錄。尚未轉 EVO 的 Git 切版案件，換電腦前必須確認提交範圍並完成 commit、push，再於另一台取得同一版本；不以只 commit 或未推送 ZIP 代替。先確認是否需要 Claude 帶著操作，已有授權不重問。Claude 接續時先讀交接再繼續，不重開提案；只換對話／模型不因此要求 push，已轉 EVO 不再推原 Git。

切版完成後，依 [Lin-EVO 接入](references/frontend-standards.md) 讀取獨立 Lin-EVO 的 `references/implementation-review.md`「切版完成後的容量與圖片格式檢核」，執行圖片大小與格式檢查及使用者提醒；本方案不另維護共用條文。

沿用案件進度檔；沒有時建立簡短 `experience-status.md`：模式、階段、確認紀錄、工具與存取狀態（Claude App、Eagle／檔案來源、人工產圖）、規格／素材／預覽路徑、驗證版本與尺寸、缺陷及下一步。不要重建整套文件。

使用者要求記錄案件時間、Token、額度百分比或加入案例庫時，必讀 [案件用量紀錄](references/usage-accounting.md)。從原始事件與同一額度視窗快照計算，跨重置要分段相加；總案件與子階段分開列示且不重複加總。只有 Token 而缺少額度起訖時，不用 Token 硬換算百分比。保留機器可讀證據與計算邊界，不把 Codex 數據換算成 Claude、API 或其他方案用量。

使用者要求推到公司 Git 或換電腦交接時，依 [Git 流程](references/git-workflow.md) 確認目標與提交範圍，詢問是否需要帶著操作；已有明確操作授權則直接執行。缺 Git 工具時提供步驟，不宣稱已推送。帳密由使用者本人輸入，不索取、不儲存；不用 force push。此流程不適用已轉 EVO 後停用的原 Git，也不因維護 Skill 自動發布客戶網站。

交付實際預覽或啟動方式、改動位置、實測結果及仍需使用者判斷的畫面。工具或資產受限時說明完成與未驗證範圍，不宣稱通過。正式部署依使用者授權。
