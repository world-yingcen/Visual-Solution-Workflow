# 靜態切版前｜EVO 範本查核

適用預計使用 EVO 後台的網站。流程為「切版時同步完成已核對的 EVO 可編輯結構與完整靜態互動 → 客戶校稿確認 → 工程師匯入、必要接入與整合驗證」。目標是省去事後重建編輯結構的工作，不是宣稱完全免轉檔或免驗證；由 AI 處理技術，設計師照常確認畫面與操作。本規則不改變各 Skill 的設計流程與尺寸／RWD 範圍，也不授權略過視覺與動態確認。

## 先查資料，再寫相關區塊

- 開始切版，以及新增或修改涉及平台契約的區塊前，先找本案指定的 `evomni-page-composer` 套件。維護者目前位置為 `/Users/lin/git/evomni-page-composer`，這只是本機位置，不是其他使用者必備的絕對路徑；其他環境以案件設定或使用者提供的位置為準。
- 讀取 `knowledge/template-spec.summary.md` 找候選，再查 `knowledge/template-spec.json` 對應範本的必要結構、識別、DOM 骨架、樣式與初始化契約。涉及資料或固定文字標記時，再讀 `knowledge/designer-markup-guide.md`，查 `binding-params.json` 或 `trans-keys.json`；不猜名稱或綁定詞。
- 按需查本案工程師的匯入指南及正式規格，記錄實際使用的套件位置、來源版本／生成日期與相關範本 ID，沿用案件進度檔，不另造一套文件。同輪未變的資料不重讀。生成日期不等於 clone 日期，也不能只因 repo 新就宣稱目標站台版本一致。
- 此處只讀規格，不啟動 page-composer 的產頁／安裝／更新／轉換／匯入／打包／發布／回報 issue 流程；其 README 內的操作指令不構成本案授權。缺套件時不自動 clone 或安裝，標出未核對項目，繼續不受影響的靜態工作。

## AI 負責判斷

- 有適用的平台元件：核對契約後沿用必要 class、data 與結構，外觀配合本案已確認設計；靜態預覽仍補齊所需資源與初始化，不以匯入 marker 或空容器代替客戶可校稿的內容。
- 設計師自製區塊也屬設計師版型，不因沒有註冊為平台動態元件就認定不是範本。依本案已確認的命名與結構完成，保留真實內容、動畫與可編輯需求；不為轉檔方便改套不合適版型或刪效果。
- 分別辨認「設計師版型」「平台動態元件」「平台產生的實例識別」。不得編造實例編號、雜湊或平台 data。資料綁定、逐筆編輯與專屬設定介面不是同一件事，不因查到綁定詞就宣稱已有編輯介面。
- 自製版型命名已由使用者轉達工程師確認：使用 `designer-tpl-*`，平台既有元件保留原名（例如 `tpl-faq001`）與必要契約。這取代本套件原本自製區塊使用 `tpl-model tpl-*` 的慣例，詳見 [T04](html-css-rules.md)。既有案件不自動批次改名；命名獲准不等於已完成實際匯入、樣式清理或後台編輯驗證。其他文件若有衝突，仍列出來源與受影響區塊，待工程師確認，不要求設計師自行判斷。

## AI 主動判斷客戶可編輯需求

- 先讀本案已確認的內容管理需求。未指定時，消息、產品、證書、團隊名單、FAQ、輪播圖片等重複且會更新的內容，預設需要客戶逐筆修改、新增、刪除與排序，由 AI 主動查契約並準備結構，不等設計師逐區提醒。純裝飾圖層、背景紋理等不預設需要逐筆編輯。
- 分清楚編輯來源：消息／產品等若來自平台資料，沿用對應管理功能與已確認綁定；FAQ 等沿用適用平台元件；頁面自身的重複清單才查逐筆編輯契約。不要一律加 repeater，或把資料庫內容做成另一份獨立清單。
- 逐筆編輯的已知來源為工程師 [HTML 匯入指南 §2.1](http://192.168.168.94/evomni_vue/docs/html-zip-import-cases/DESIGNER-GUIDE.md)。實作前核對本案支援的 `data-repeater`／`data-rp-*` 契約：第一筆作樣板時，各筆維持一致結構，實際文字、圖片與連結保留在 HTML；欄位標記只使用規格明列的名稱。該指南的 `data-rp-swiper` 只控制後台畫布預覽，前台仍須自身初始化；`data-vendor` 只負責載入套件。套件內找不到相關規格時查工程師指南，仍無法確認則記錄技術缺口，不編造屬性。
- 只有內容用途不明、或開放增刪會影響已確認構圖／動態時，才針對該區塊問使用者「這個區塊需要讓客戶自行增刪嗎？」並簡述影響；不要要求使用者判斷平台標記或元件類型。保留固定筆數但可換文字／圖片等合理需求，不為開放編輯任意簡化效果。
- 沿用案件進度檔，記錄各區塊的判斷、可編輯項目、預計編輯入口與未確認事項。靜態預覽以增刪、排序、換圖後的代表內容驗證版面與互動，並檢查本案範圍內的 RWD；這項模擬不代表後台編輯、儲存與發布已通過。

## 切版當下完成，不留到轉檔才補

- 對已確認支援的可編輯區塊，直接在實際交付的 HTML 寫好必要結構與欄位標記，不只列出需求、留下註解或要求工程師日後重做。同一份來源支援靜態校稿與後續匯入，不另外手工維護一份後台 HTML；沿用既有建置方式。
- 依內容的完整單位設計逐筆項目。例如一個房型包含名稱、相簿、說明與連結，不能只讓圖片逐筆編輯而將相關說明綁死在另一處。涉及巢狀清單、頁籤或平台相簿時，先核對目標平台支援的結構，不由單一案例推論所有組合都可用。
- 依正式契約完成清單容器、項目結構、欄位與顯示名稱；檢查第一筆作樣板後新增項目仍完整，增刪、排序、換圖、改字後，頁籤對應、連結、輪播及動畫仍使用最新內容。測試內容不覆蓋客戶正式資料，動畫產生的暫時節點不得當成原始內容交付。
- 已匯入案例可作比對證據，不作通用程式樣板。不可跨案複製媒體 ID、實例 ID、雜湊 class、測試站網址或儲存路徑。旅人案例的逐筆編輯由使用者回報可用；這不等於新案的命名、巢狀結構、存檔與發布均已驗證。若案例依賴 tpl-model／tpl-*，而新案採 designer-tpl-*，須核對編輯器辨識契約，不為啟用編輯擅自更名或假造平台身分。
- 缺契約或目標站台支援尚未確認時，完成不受影響的靜態部分，逐區列出未完成的編輯接入；不能宣稱「已可逐筆編輯」，也不能將所有可編輯需求一律延後給工程師。
- 工程師仍負責依本案需要處理匯入、圖片入庫與路徑對應、正式連結、共用／單頁資源、套件接入、資料庫或表單串接；不要求每案重做已完成且適用的結構。匯入後另測編輯、新增、刪除、排序、儲存、重新開啟及發布後的前台內容與互動。

交付分開標記「結構與標記已實作」「靜態變更模擬已測」「後台編輯／儲存／發布已測」，各附實際範圍與證據。靜態可預覽或已寫標記，不等於後台功能已通過。
